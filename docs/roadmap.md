# Development roadmap

The core deliverable is a local educational prototype and a controlled comparison of three authorisation policies. Each phase below has a completion check. Phase 2 defines the requirements for later implementation.

## Core phases

| Phase and status | Objective | Scope and dependencies | Deliverables | Acceptance criteria |
| --- | --- | --- | --- | --- |
| 1. Project Foundation — Implemented | Establish a deterministic policy proof of concept | Python package, synthetic identity and delegation records, exact-pair decision logic and unit tests. No prior phase | Source, tests, demo, setup and initial design notes | Existing suite passes. Demo allows the delegated meeting read and denies the out-of-task salary read |
| 2. System & Threat Model Design — Complete | Establish the trust model and evaluation protocol before adding runtime code | Review Phase 1. Define architecture, threat model, fixture policy and experimental methodology | Five Phase 2 design documents and updated README | Diagrams and links check out. Every legitimate task has a consistent permission path. Planned features and evaluation expectations are labelled |
| 3. Sandbox Environment — Implemented | Build a resettable synthetic resource environment | Depends on Phase 2 tool and resource contracts. Implements a fixed catalogue, document operations, inbox and outbox in memory | Versioned fixtures, seven trusted handlers, reset and snapshot support, tests and a trusted demo. [Sandbox design](sandbox-design.md) | Fixtures reset deterministically. Operations cannot reach uncontrolled paths or external destinations. Writes and deletes affect only named sandbox slots |
| 4. Identity & Delegation — Implemented | Bind a run to trusted principals and a revocable task | Depends on Phase 2 identity and lifecycle rules and Phase 3 resource IDs. Uses local synthetic session authentication and trusted agent assignment | Versioned identity store, session and run binding, delegation manager, context validation, tests and a trusted demo. [Identity and delegation design](identity-delegation-design.md) | Reject invalid principals and delegations. Verify activation, completion, expiry and revocation independently of shared run validation |
| 5. Authorisation Gateway — Implemented | Enforce decisions on the controlled tool-call path | Uses the Phase 3 sandbox and Phase 4 authority records. Provides a shared registry and validator, PDP and PEP, three policy modes and required pre-dispatch audit persistence | Gateway, private sandbox executor, JSON Lines journal, enforcement tests and a trusted demo. [Gateway design](gateway-design.md) | Malformed requests and denials cause no dispatch. Allowed calls use the same canonical arguments. Failure, stale context and revocation cases fail closed. Legitimate fixture operations remain possible |
| 6. LLM Integration — Implemented, live inference pending | Exercise the gateway through a model-facing runtime | Uses the Phase 5 gateway with provider-independent replay, stub and opt-in local Ollama | Bounded conversation loop, structured observations, normal-task demos and offline protocol tests. [Integration design](llm-integration-design.md) | Each backend uses the same gateway entry point. The stub completes normal tasks. Run a separate inference smoke test when a compliant local service is available |
| 7. Attack Scenarios — Planned | Freeze a reproducible corpus of synthetic cases and labels | Depends on Phase 2 threat model and Phases 5–6 interfaces. Define controlled direct and indirect input conditions and deterministic replay cases | Versioned fixtures, case manifests, target effects and independent labelling rules | Each case names its task, initial state, objective and expected labels. Every fixture stays within the synthetic lab |
| 8. Audit Logging & Security Testing — Planned | Verify traceability and enforcement across failure cases | Depends on gateway instrumentation and Phase 7 manifests. Extend the minimum decision log with safe canonical arguments, dispatch, outcome and independent observations | Correlated structured audit events, security regression suite and completeness checks | Denials, allowed operations and failures are traceable. Tests cover no-dispatch denials, revocation, argument restrictions, search disclosure, caller context integrity and audit faults. Logs exclude raw contents |
| 9. Experimental Evaluation — Planned | Compare the three policies using replay and end-to-end trials | Depends on Phases 5–8. Apply the frozen protocol to the isolated synthetic sandbox using matched backend settings | Run manifests, observations, metrics and analysis | Report raw counts, denominators, latency distributions, variability and missing observations. Report primary ASR and objective-specific results separately. If LLM inference is unavailable, report replay and stub results separately and mark end-to-end LLM results unavailable |
| 10. Demo & Final Report — Planned | Present the implemented controls, evidence and limits | Depends on Phase 9 results and the verified prototype. Use the course's project scope | Local demo, reproducibility instructions and final report | The demo shows a legitimate task and a mediated unauthorised request. The report traces claims to actual observations and states the study limits |

## Optional extensions

- Additional local model checkpoints or alternative static profiles for sensitivity analysis after the main comparison.
- Explicitly configured hosted inference using approved synthetic inputs only under the [model adapter constraints](system-design.md#model-adapter).
- A local fixture editor or audit viewer to support demonstrations.
- Content provenance tracking or richer policy predicates as a separate information-flow investigation.

Core acceptance uses the three fixed policy modes and the synthetic tasks. Production identity infrastructure, external mail, real accounts and arbitrary filesystem or shell access remain outside the project scope.
